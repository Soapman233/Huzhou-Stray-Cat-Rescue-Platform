# 核心算法说明与局限分析

> 本文档梳理 HZSCA 平台两个核心算法（**猫咪智能匹配** 与 **领养风险评分**）的设计细节、
> 已知局限与改进方向，可作为毕业论文「算法设计与分析」「不足与展望」章节的素材。

---

## 一、猫咪智能匹配算法

实现位置：`hzsca-springboot/hzsca/src/main/java/com/hzsca/service/impl/MatchServiceImpl.java`
单元测试：`src/test/java/com/hzsca/service/impl/MatchServiceImplTest.java`（19 个用例）

### 1.1 设计

采用**「硬性排除 + 六维加权打分」**两阶段模型。

**第一阶段 · 硬性排除（一票否决）**

| 条件 | 排除原因 |
|------|---------|
| 用户过敏 且 猫咪掉毛等级 > 用户容忍上限 | 健康风险 |
| 家中有孩子 且 猫咪不适合与儿童相处 | 安全风险 |
| 家中有其他宠物 且 猫咪不适合与宠物共处 | 相处风险 |
| 用户不接受特殊照护 且 猫咪需要特殊照护 | 履约风险 |
| 居住空间等级 < 猫咪空间需求等级 | 环境不适配 |

**第二阶段 · 六维加权打分**

| 维度 | 默认权重 | 归一化方式 |
|------|---------|-----------|
| 活动量 `activity` | 1.0 | 陪伴时长映射用户活跃度(1~5)，与猫咪活跃度做 `1 − |diff|/4` |
| 亲人度 `affection` | 0.6 | 按偏好（黏人/独立/不限）对亲人度做正向或反向映射 |
| 掉毛容忍 `shedding` | 1.2 | 未超容忍上限得满分，超出按 `1 − (shedding−max)/4` 衰减 |
| 空间 `space` | 1.0 | 满足需求得满分，不足按 `1 − (need−home)/2` 衰减 |
| 新手友好 `beginner` | 1.0 | 零经验用户 × 非新手友好猫 → 0 分 |
| 作息 `personality` | 1.0 | 夜班用户 × 夜行猫 得满分，否则 0.6 |

最终得分：`score = Σ(权重ᵢ × 匹配度ᵢ) / Σ权重ᵢ × 100`，四舍五入保留 1 位小数，
按得分降序返回 Top-N（默认 10，上限 50）。权重可由 `match_weights` 表动态覆盖。

### 1.2 已知局限

**局限 1：`space` 维度不具备区分度（实测确认）**

`matchSpace()` 中对未被排除的猫咪**恒返回 1.0**。原因：空间不足的情况
（`homeSizeLevel < spaceNeedLevel`）已在第一阶段被硬性排除拦截，因此能进入打分阶段的猫
必然满足 `homeSize >= spaceNeed`，函数直接返回满分。该维度实际对排序结果**没有任何影响**，
却仍占据 1.0 的权重，稀释了其他有效维度的区分能力。

**局限 2：维度间无交互，模型表达力有限**

采用线性加权平均，无法表达「条件组合」语义。例如「空间小 但 陪伴时间充足」本应可补偿，
但线性模型无法体现这种交互。

**局限 3：权重依赖人工设定**

默认权重由人工经验给定，`match_weights` 表虽支持动态配置，但**没有任何机制用于学习最优权重**。

**局限 4：硬性排除可能导致候选过少（冷启动）**

排除规则是「一票否决」，若用户条件较为特殊（如过敏 + 家中有孩子 + 居住空间小），
可能返回空列表。当前实现未提供「放宽条件后重试」或「给出最接近的备选」的降级策略。

**局限 5：未利用行为反馈闭环**

系统已通过 `user_behavior` 表采集用户行为（浏览、申请等），但匹配算法**完全没有使用**这些数据，
无法从「用户最终领养了哪只猫」中学习。

### 1.3 改进方向

1. **修复 `space` 维度**：将其改为「软约束」——把空间不足从硬性排除降级为强扣分项，
   使该维度真正参与排序；
2. **引入行为反馈**：用 `user_behavior` 构建隐式反馈，做**点击率预估 / 学习排序（LTR）**；
3. **模型升级**：在数据量允许时，用逻辑回归或 GBDT 替代人工权重，以「是否最终申请/领养」为标签；
4. **多样性重排**：在 Top-N 结果上做 MMR（最大边际相关）重排，避免推荐同质化；
5. **冷启动降级**：排除后候选不足时，按「违反规则数」升序给出次优推荐并明确提示原因。

## 二、领养风险评分算法

实现位置：`hzsca-springboot/hzsca/src/main/java/com/hzsca/service/impl/RiskScoringServiceImpl.java`
单元测试：`src/test/java/com/hzsca/service/impl/RiskScoringServiceImplTest.java`（22 个用例）

### 2.1 设计

以 100 分为基准的**规则化扣分模型**：

| 因素 | 分值变化 |
|------|---------|
| 家庭成员过敏 | −25 |
| 家庭成员哮喘 | −15 |
| 家中有人吸烟 | −10 |
| 工作时长 ≥ 12h / ≥ 10h | −12 / −8 |
| 工作时长 ≤ 6h | +3 |
| 家庭月收入 < 3000 / ≥ 8000 | −10 / +5 |
| 有养宠经验 / 无经验 | +2 / −5 |
| 接受定期回访 / 拒绝回访 | +5 / −8 |

结果截断到 `[0, 100]`：`≥80 → LOW`，`60 ~ 79 → MEDIUM`，`< 60 → HIGH`，
并保留每一项的加减分明细作为审核依据。

### 2.2 已知局限

**局限 1：下界截断分支为死代码（实测确认）**

```java
if (score < 0) score = 0;   // 该分支永远不会被执行
```

所有扣分项之和最大为 `25 + 15 + 10 + 12 + 10 + 5 + 8 = 85`，
因此理论最低分为 `100 − 85 = 15`，**分数永远不可能小于 0**。
该行属于防御性代码，实际不可达；单元测试中也无法构造出触发该分支的输入
（测试改为验证「最低分为 15」这一真实边界）。

> 说明：保留该行不影响正确性，但会让人误以为存在更低的分数区间。

**局限 2：阈值与分值为人工经验设定**

各因素的分值（如过敏 −25）与风险档位阈值（80 / 60）均为主观设定，
**缺乏数据支撑**，也未做过敏感性分析或交叉验证。

**局限 3：未做特征交互与非线性建模**

同样是线性可加模型，无法表达「收入低 **且** 拒绝回访」这类组合风险的叠加放大效应。

**局限 4：未与真实审核结果做校验**

`adoption_request` 表中已积累审核结果（APPROVED / REJECTED），
但评分模型从未与这些**真实标签**做过一致性校验（如 AUC、准确率），
因此无法量化「评分是否真的能预测审核结论」。

**局限 5：存在被规避的可能**

问卷由申请人自行填写，缺乏交叉验证（如收入与工作单位），存在**主观填报偏差**。

### 2.3 改进方向

1. **删除或标注死代码**，避免误导（当前已在单元测试中显式说明该边界）；
2. **数据驱动建模**：以历史审核结果（APPROVED / REJECTED）为标签，
   训练逻辑回归 / GBDT，用 **AUC、KS** 评估，并输出特征重要性；
3. **分值校准**：用 WOE / IV 分析重新标定各因素分值，替代人工拍定；
4. **增加一致性校验任务**：定期比对「模型风险等级」与「人工审核结论」的偏离度，发现规则失效；
5. **引入第三方校验字段**（可选）：如单位性质、居住证明等，降低主观填报影响。

## 三、小结

| 算法 | 亮点 | 主要短板 |
|------|------|---------|
| 智能匹配 | 两阶段过滤 + 可配置权重的多因子模型，工程上可解释、可运营 | `space` 维度失效、权重靠人工、未利用行为反馈 |
| 风险评分 | 规则清晰、明细可追溯、结果直接入库辅助审核 | 死代码分支、阈值无数据支撑、未与真实标签校验 |

两者的共同改进路径是：**从「人工规则」走向「数据驱动 + 人工规则兜底」**，
并补齐离线评估指标，使算法效果可度量、可迭代。
